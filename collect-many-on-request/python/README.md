# INNORIX Transfer Builder — Python Guide

This guide explains how to configure, run, and troubleshoot the Python implementation of an INNORIX Transfer Builder example.

The Python program (`combo_builder.py`) reads transfer settings from a `.env` file and sends the configured requests to the INNORIX Platform API. This lets you adjust the transfer configuration without editing the source code.

This guide covers the Python environment and common execution steps. The README in each builder directory explains what that particular transfer scenario does and which settings it requires.

## Before You Start

If this is your first time using INNORIX, start with the [repository README](../../README.md). It explains the overall workflow, INNORIX Platform setup, API key access, and device registration.

Before running a builder example, make sure you have:

- An INNORIX Platform account and access to the appropriate workspace.
- A supported authentication method, preferably an API key.
- The required source and destination devices registered and connected in the Platform.
- The Python example files from the selected builder directory.
- The configuration values required by that builder, as described in its [builder-specific README](../README.md).

A transfer generally requires at least a source device and a destination device. The exact configuration depends on the selected builder scenario.

## Requirements

- **Python 3.8 or later**
- The `requests` package
- A terminal or command-line interface
- Access to the selected builder's Python directory

Check your Python version:

```bash
python --version
```

If `python` is not available on your PATH, try `py --version` on Windows. Use the same Python command when installing dependencies and running the example so the package is installed in the environment that executes the script.

The script uses `requests` for HTTP requests and does not require other third-party Python packages.

## 1. Understand the Files

The Python directory typically contains the following files:

| File | Purpose |
|---|---|
| `combo_builder.py` | Python program that submits and monitors the configured operation. |
| `.env` | Configuration generated by the Transfer Builder or prepared locally for this example. It may contain placeholder values that you must replace. |
| `.env.builder.example` | Reference template documenting the available configuration options and their meanings. |

### Important: Keep the Generated `.env`

If the downloaded builder example already includes a generated `.env`, **review and edit that file rather than replacing it with `.env.builder.example`**. The generated file represents the configuration selected in the Transfer Builder. Replacing it with the general template may remove those choices.

Use `.env.builder.example` as a reference when you need to understand a setting or prepare a configuration file because `.env` is missing.

## 2. Review and Configure `.env`

Open `.env` and check the values for your selected builder before running the program. The generated file may include placeholders such as `<deviceId>` or example paths; replace them with values from your own INNORIX Platform environment.

Common settings include:

| Setting | Purpose |
|---|---|
| `INNORIX_API_KEY` | Long-lived user API key used to authenticate API requests. |
| `INNORIX_WORKSPACE_ID` | Workspace used for API requests. |
| `SOURCE_ID` / `SOURCE_PATH` | Source device ID and path on that device. |
| `TARGET_ID` / `TARGET_PATH` | Destination device ID and path on that device. |

The settings required depend on the transfer type. For example, sending to multiple devices may require a list of target device IDs, while collecting from multiple devices may require a list of source device IDs. See the selected builder's README and `.env.builder.example` for the complete settings reference.

### This Example's `.env` Settings

Builder page: [collect-many-on-request](https://innorix.com/en/builder/collect-many-on-request) — several source devices → one target device, runs when an external system calls the trigger URL the program prints.

The transfer type and start condition are fixed in this example's code, so `TRANSFER_TYPE` and `START_WHEN` are not used. Set these keys in `.env`:

| Key | Required | Value in `.env` | Description |
| --- | --- | --- | --- |
| `INNORIX_API_KEY` | ✔ (or token / login) | — | User API key, sent as `x-api-key` (or set `INNORIX_ACCESS_TOKEN`, or `INNORIX_EMAIL` + `INNORIX_PASSWORD`) |
| `INNORIX_WORKSPACE_ID` |  | — | Workspace to act in |
| `SOURCE_IDS` | ✔ | `<deviceId>,<deviceId>,<deviceId>` | Source device IDs, comma separated |
| `SOURCE_PATHS` | ✔ | `C:/data/out,/data/out,/data/out` | One path for every source, or one per source in the same order |
| `TARGET_ID` | ✔ | `<deviceId>` | Target device ID |
| `TARGET_PATH` | ✔ | `C:/collect` | Path on the target device |
| `SOURCE_IS_DIR` |  | `true` | `false` when the source path is a single file |
| `NAME` |  | `collect-many-on-request` | Automation name |
| `FIRE_TRIGGER` |  | `false` | `true` calls the trigger URL once right after creating it |
| `SCHEDULE_TZ` |  | `Asia/Seoul` | Timezone of the automation |
| `SAVE_PATH` |  | `root` | `root` (no subfolder) · `date` (run-date subfolder) · `device` (subfolder per source device name) |
| `DUPLICATE_ACTION` |  | `overwrite` | `overwrite` · `rename` · `skip` when the target has a file with the same name |
| `INTEGRITY` |  | `true` | Verify each file after the transfer |

Every key, with comments: `.env.builder.example`.

### Understand Device Paths

`SOURCE_PATH` and `TARGET_PATH` refer to paths on the configured source and destination devices. They do **not necessarily refer to folders on the computer running this Python program**.

For example, `C:/data/out` is a path to be interpreted in the source device's environment, while `C:/incoming` is interpreted in the destination device's environment. Confirm that the paths exist and that the relevant devices and agents have the required access.

### Review Optional Integrations and File Options

Before execution, also review any enabled options in `.env`, including:

- Message notifications, such as Slack or Teams
- Virus scanning
- Email notifications
- Monitoring
- HTTP API, command, or script actions
- File filters, destination subfolders, duplicate-file behavior, and integrity verification

Some integrations require provider-specific configuration. A setting such as `ON_MESSAGE=true` or `ON_VIRUS_SCAN=true` does not by itself guarantee that the integration is ready to run. Check the relevant `*_CONFIG` fields and the provider's required settings. The `.env.builder.example` describes the available options; provider rules can also be retrieved through `GET /api/integrations/rules/{type}` where supported by your environment.

**Review these settings before running the program.** Depending on the configuration, the program may create or reuse workspace-level integrations, create an automation, start an immediate operation, or set up a scheduled or externally triggered operation.

## 3. Configure Authentication

Configure **one** supported authentication method in `.env`:

| Configuration | Description |
|---|---|
| `INNORIX_API_KEY` | Long-lived user API key sent in the `x-api-key` request header. Recommended for most use cases. |
| `INNORIX_ACCESS_TOKEN` | Short-lived JWT sent in the `Authorization: Bearer` header. |
| `INNORIX_EMAIL` and `INNORIX_PASSWORD` | Credentials used by the program to sign in and retrieve an access token. |

### Obtain an API Key

1. Sign in to the INNORIX Platform.
2. Open the profile menu at the bottom-left of the product interface.
3. Select **Developer**.
4. Copy the **API Key** and set it as `INNORIX_API_KEY` in `.env`.
5. Copy the **Workspace ID** shown in the same dialog and set `INNORIX_WORKSPACE_ID`.

Unless your environment requires a different endpoint, keep the base URL at its default:

```dotenv
INNORIX_BASE_URL=https://app.innorix.com
```

An API key can also be created through `POST /api/auth/api-keys`. This request requires a Bearer access token and no request body; the generated key is returned as `data.apiKey`.

For more information, see the [INNORIX Developer Center](https://innorix.com/en/developers), [Quick Start](https://innorix.com/en/developer#dev-api-quick), and [API Reference](https://innorix.com/en/developer/api).

### Protect Credentials and Logs

**Never commit real credentials to Git.**

- Keep the local `.env` file out of version control. Verify that `.env` is excluded by `.gitignore`.
- Commit the `.env.builder.example` template, not a `.env` containing real keys, tokens, passwords, or provider secrets.
- Do not publish API keys or external trigger keys in screenshots, terminal output, tickets, or logs.
- If using `DEBUG=true`, review the program's debug behavior first. Debug output includes request and response details; do not share logs until you have checked them for sensitive information.
- An external trigger URL and its associated key should be treated as secrets because anyone with the required trigger information may be able to start the configured operation.

## 4. Run the Python Example

The script requires the `requests` package. Install it using the same Python command that you will use to run the example.

**macOS / Linux**

```bash
python -m pip install requests
python combo_builder.py
```

**Windows (PowerShell)**

```powershell
py -m pip install requests
py combo_builder.py
```

If you already have a builder-generated `.env`, edit it before running the script. If `.env` is missing, create it from `.env.builder.example` and fill in the required settings.

By default, the script looks for `.env` in the Python example directory. To use a different configuration file, pass its path as an argument:

```bash
python combo_builder.py path/to/other.env
```

On Windows, use `py` instead of `python` if that is the command configured on your system:

```powershell
py combo_builder.py path\to\other.env
```

The script reads operating-system environment variables as well as the `.env` file. If the same setting is already defined in the operating-system environment, that value takes precedence over the value in `.env`.

## 5. Verify the Result

After execution:

1. Review the terminal output for configuration errors, API errors, and the operation or transfer status.
2. Open the INNORIX Platform and check the relevant automation or transfer status.
3. For file transfers, confirm that the expected files arrived at the configured destination.
4. For scheduled, recurring, chained, synchronization, or external-trigger scenarios, verify the configuration and execution status appropriate to that scenario rather than expecting an immediate file transfer.
5. If an integration is enabled, verify its own configuration and outcome as well as the transfer result.

The expected output depends on the example, its configuration, and the execution condition. Refer to the builder-specific README for scenario-specific expectations.

## 6. Troubleshooting

| Symptom | What to check first |
|---|---|
| `python` or `py` is not recognized | Confirm Python is installed and available on your PATH. On Windows, try the `py` launcher. |
| `No module named 'requests'` | Install `requests` with the same interpreter used to run the script: `python -m pip install requests` or `py -m pip install requests`. |
| The configuration file cannot be found | Check that `.env` exists in the Python example directory, or provide a valid path to another `.env` file. |
| Authentication fails | Check the selected authentication method, API key or token, Workspace ID, and base URL. Do not paste real credentials into support messages. |
| A device or path cannot be accessed | Confirm source and destination device IDs, device connectivity, paths, and agent access. Remember that paths belong to the configured devices. |
| An immediate transfer does not start | Review the required device/path settings in `.env` and the operation status in the Platform. |
| A scheduled or recurring operation does not run now | Check the configured time, timezone, recurrence settings, and the automation status. Delayed execution may be expected. |
| A timezone is unavailable when calculating a recurrence | The script may fall back to the computer's local time if the named timezone database is unavailable. Verify the runtime environment and schedule timezone. |
| An integration is created but does not work | Check the provider type and required fields in the corresponding `*_CONFIG` value. |
| The files transferred differ from expectations | Review file filters, source and destination paths, duplicate-file behavior, save-path settings, and integrity verification. |

For scenario-specific configuration, consult the selected builder's README and `.env.builder.example`.
