# INNORIX Transfer Builder Artifacts

Welcome! This repository helps you take the code generated by the [INNORIX Transfer Builder](https://innorix.com/en/builder) and run it in your own environment.

The Builder lets you choose a transfer scenario and configure its options. It provides a runnable example in **Java, Python, C#, and Node.js**. In these examples, the script is designed to stay unchanged while the selected transfer settings live in the `.env` file next to it. This repository keeps each Builder configuration in its own directory, so you can find the scenario you need, choose your language, and retrieve only the files you plan to use.

You do not need to know every INNORIX API detail before starting. Follow the steps below in order, and use the language-specific `README.md` for the exact setup and run commands for your selected example.

## Start Here

Choose the path that best describes you:

- **New to INNORIX?** Start with [Prepare your INNORIX Platform environment](#1-prepare-your-innorix-platform-environment).
- **Already have an INNORIX account and connected devices?** Go to [Choose and retrieve a builder](#2-choose-and-retrieve-a-builder).
- **Looking for a specific scenario?** Browse the [Builder Directory Index](#builder-directory-index).

### How the pieces fit together

1. **Transfer Builder page** — choose what you want to do and configure the options.
2. **Builder directory** — the last part of the Builder page URL matches the folder name in this repository.
3. **Language directory** — choose `java/`, `python/`, `csharp/`, or `nodejs/`.
4. **Configuration file** — supply the API connection details and transfer settings required by that example.
5. **INNORIX Platform** — the code calls the Platform API and uses the devices and paths you configured.

## Before You Begin

For a typical device-to-device transfer, you will need an INNORIX Platform account, an API key, and at least two registered and connected devices. Some upload, download, or other scenarios may have different prerequisites, so check the Builder page for your selected scenario.

### 1. Prepare Your INNORIX Platform Environment

#### Create or sign in to your account

Open [INNORIX Platform](https://innorix.com/en/) and create an account, or sign in if you already have one. You will use the Platform console to manage your workspace and connected devices.

#### Get your API key

1. Sign in to the INNORIX Platform.
2. Open **My Profile > Developer** (the profile menu is at the bottom-left of the product interface).
3. Copy or generate the API key according to the instructions shown in the console. The same area may also show your **Workspace ID**, which some examples require.

An API key identifies your API access when the generated code makes requests to INNORIX. Treat it like a password: do not share it publicly or commit it to Git.

For detailed guidance, visit the [INNORIX Developer Center](https://innorix.com/en/developers).

#### Register and connect your devices

For a standard transfer, prepare at least two devices:

- **Source** — where the files or folders are read from.
- **Target** — where the files or folders are written to.

In the Platform console, go to **Devices > Connect Device** and follow the instructions for the operating system or storage environment you want to use. PCs and servers may require the INNORIX Agent; object-storage setup depends on the storage type. Confirm that the devices are connected or online before running a transfer.

You will need the correct device IDs and valid source/target paths when configuring the example. A source path must exist and be accessible to the source device; the destination path must be valid for the target device.

For device registration and connection steps, see the [INNORIX Product Guide](https://innorix.com/en/product-guide).

### 2. Choose and Retrieve a Builder

1. Open the [INNORIX Transfer Builder](https://innorix.com/en/builder) and choose the scenario that matches your task.
2. Configure the required options on the Builder page.
3. Note the last part of the page URL. For example, `https://innorix.com/en/builder/send-one-now` maps to the `send-one-now/` directory in this repository.
4. Select your preferred language: Java, Python, C#, or Node.js.
5. Follow [Select a Builder Folder](#select-a-builder-folder) to retrieve only the directory you need.

### 3. Configure and Run the Code

Inside the selected language directory, start by reading its `README.md`. That file should tell you which runtime or SDK is required, how to prepare configuration, how to install dependencies, which command to run, and what successful output looks like.

Most examples use `.env.builder.example` as a configuration template and `.env` for local runtime settings. The exact fields vary by builder. Depending on the scenario, you may need an API URL, API key or credentials, Workspace ID, device IDs, source and target paths, scheduling options, or file-handling options. Use the selected example's template and README as the source of truth—do not assume every field is required for every builder.

**Before running:** make sure the API key is available to the code, the required devices are connected, and the configured paths and options match your intended transfer.

## A Few Terms You Will See

| Term | Meaning |
|---|---|
| **Builder** | The page where you choose a transfer scenario and its options. |
| **Builder directory** | The repository folder matching the last part of a Builder page URL, such as `send-one-now/`. |
| **Language directory** | The `java/`, `python/`, `csharp/`, or `nodejs/` folder containing the code for that language. |
| **API key** | A credential used by the code to authenticate API requests to INNORIX. Keep it private. |
| **Workspace ID** | Identifies the INNORIX workspace the API request should use, when required by the example. |
| **Device ID** | Identifies a device registered in the Platform. Use the ID of the actual source or target device. |
| **`.env.builder.example`** | A template that documents the configuration values supported by the generated example. |
| **`.env`** | A local configuration file used by examples that load settings from environment variables or a `.env` file. Do not commit sensitive values. |
| **Git Sparse Checkout** | A Git feature that keeps selected directories in your working folder without checking out every builder directory. It does not restrict repository access. |

## Repository Structure

Builder directories are located directly at the repository root. Their names match the final path segment of the corresponding Builder page URL; there is no additional `types/` or `builders/` parent directory. Each builder contains language-specific directories.

For example, when you open the Java version of a builder, you may see files like these:

```text
transfer-builder-artifacts/
├── README.md
├── send-one-now/                     # Matches /builder/send-one-now
│   ├── java/
│   │   ├── README.md                 # Setup and run instructions for Java
│   │   ├── ComboBuilder.java          # Generated Java source
│   │   ├── .env.builder.example       # Configuration template/reference
│   │   └── .env                      # Review before sharing or committing
│   ├── python/
│   ├── csharp/
│   └── nodejs/
├── send-one-now-follow-up/
│   ├── java/
│   ├── python/
│   ├── csharp/
│   └── nodejs/
└── ...
```

The exact files can vary by builder and language. Use the `README.md` and configuration template inside the selected language directory for instructions specific to that example.

## Select a Builder Folder

Git Sparse Checkout lets you keep only selected directories in your local working folder. It is useful when you want one builder or one language version instead of every example in the repository.

### What you need

- Git 2.25 or later.
- Permission to access this GitHub repository. If it is private, your GitHub account must be authorized.
- A terminal: Git Bash on Windows, or Terminal on macOS/Linux.

### Step 1 — Clone the repository

Copy the repository's HTTPS URL from GitHub. Replace `<ORG>` with the GitHub organization or account that owns this repository:

```bash
git clone --filter=blob:none --no-checkout https://github.com/<ORG>/transfer-builder-artifacts.git
cd transfer-builder-artifacts
```

If you have already cloned the repository, open a terminal in that local repository and continue to the next step.

### Step 2 — Select one builder and language

For example, to work only with the Java code for `send-one-now`, run:

```bash
git sparse-checkout init --cone
git sparse-checkout set send-one-now/java
git checkout main
```

Replace `send-one-now` with the exact directory name shown in the [Builder Directory Index](#builder-directory-index). To choose another language, replace `java` with one of the following:

| Language | Directory |
|---|---|
| Java | `java/` |
| Python | `python/` |
| C# | `csharp/` |
| Node.js | `nodejs/` |

After the command completes, you should see the selected language directory and root-level files such as this repository's `README.md`. You will not see every builder's files in the working directory.

### Step 3 — Select a whole builder or more than one builder

To include all languages for one builder instead, use its builder directory:

```bash
git sparse-checkout set send-one-now
```

To include two builders, specify both:

```bash
git sparse-checkout set send-one-now send-many-now
```

The `set` command replaces your previous selection. To keep your current selection and add another directory, use `git sparse-checkout add`, for example:

```bash
git sparse-checkout add collect-many-now
```

### Step 4 — Open the code and follow its README

Open the selected language directory in your editor. Common file names include:

| Language | Example files |
|---|---|
| Java | `ComboBuilder.java` |
| Python | `combo_builder.py` |
| C# | `ComboBuilder.cs` |
| Node.js | `combo_builder.js` |

These names reflect the current example conventions; check the files in your selected folder if the names differ. Read that folder's `README.md` before running the code. It should provide the correct runtime version, setup commands, configuration steps, execution command, and expected result for that particular example.

## Configure Your Example

Use this checklist for the selected language directory. The exact fields and commands are documented in that directory's `README.md` and `.env.builder.example`.

1. **Check prerequisites.** Install the runtime or SDK version required by the example.
2. **Review the configuration template.** Open `.env.builder.example` and read the comments and descriptions before changing values.
3. **Prepare the local `.env` file if required.** If no usable `.env` is present, create it from the template as described in the language README. For Bash, this is commonly `cp .env.builder.example .env`; in PowerShell, use `Copy-Item .env.builder.example .env`. If the Builder has already supplied a `.env`, inspect its values and follow the language README rather than overwriting it blindly.
4. **Fill in environment-specific values.** These may include API URL, API key or credentials, Workspace ID, source/target device IDs, paths, scheduling settings, or file options. Use real values from your Platform workspace; do not copy illustrative values unchanged.
5. **Protect credentials.** A `.env` containing real secrets should remain local and must not be committed. Before committing any generated `.env`, inspect it for API keys, passwords, access tokens, workspace details, device identifiers, and customer-sensitive paths. Keep only values that are safe and intended to be shared.
6. **Install dependencies and run.** Follow the exact commands in the language README. Projects can use different tools (for example, npm, pip, Maven, or the .NET CLI), so do not assume that one command works for all four languages.

### What success looks like

After running the example, check both sides of the process:

- The terminal or application output shows that the request or transfer completed without an unresolved error.
- The expected file or folder is present at the destination.
- When applicable to the selected scenario, the INNORIX Platform console shows the corresponding run or transfer result.

If the run fails, see [Troubleshooting](#troubleshooting) before changing the generated source code. For configuration-based examples, adjust supported settings in `.env` first; edit generated source code only when you have a specific reason to do so.

## Synchronize Updates

To retrieve updates from the remote `main` branch, run this from your local repository directory:

```bash
git pull origin main
```

Git updates the selected paths in your working directory. If this repository uses a different default branch, replace `main` with the correct branch name. If you have made local changes to tracked files, commit or back them up before pulling so you can resolve any merge conflicts safely.

## Verify the Transfer

If your code runs but the expected files do not arrive, check these items in order:

1. **Device status:** confirm the source and target devices are registered and connected in INNORIX Platform.
2. **Device IDs:** confirm the configured IDs refer to the intended source and target devices.
3. **Paths and permissions:** confirm the source path exists and the destination path is valid and accessible to the connected devices.
4. **Authentication and workspace:** check that the API key or credentials and Workspace ID match the environment where the devices are registered.
5. **Builder options:** review filters, duplicate-file behavior, schedule settings, and follow-up actions selected in the Builder.
6. **Result status:** inspect the application output and, where applicable, the run or transfer details in the Platform console.

For device-specific steps, see the [INNORIX Product Guide](https://innorix.com/en/product-guide/). For API authentication and implementation information, see the [INNORIX Developer Center](https://innorix.com/en/developers/).

## Troubleshooting

| What you see | What to check first |
|---|---|
| Git cannot clone the repository | Confirm the URL, GitHub sign-in, network access, and repository permission. |
| The expected folder is missing | Check the folder slug against the index and rerun `git sparse-checkout set <builder>/<language>`. |
| Authentication fails | Confirm the API key or credential is valid and configured using the method expected by the selected example. Never paste the secret into a public issue. |
| The API reports that a device cannot be found | Confirm the Workspace ID and device IDs belong to the intended Platform workspace, and that the devices are registered. |
| The transfer cannot find a file or folder | Confirm the source/target paths and the permissions of the connected devices. |
| The code will not start | Check the required runtime/SDK version, dependencies, and execution command in the selected language README. |
| The transfer starts but does not complete as expected | Review the application output, Platform run status, transfer options, and the builder's follow-up settings. |

When asking for help, include the builder directory, language, the step you were following, and the relevant error message. Remove API keys, passwords, tokens, and other sensitive values from logs before sharing them.

## Security and Repository Access

- **Sparse Checkout is not an access-control feature.** It controls which files appear in your working directory; it does not prevent a user with repository access from reading other folders or Git history.
- If the repository is private, a user must have permission to access the repository itself. Sparse Checkout does not grant folder-specific permissions.
- Never commit API keys, passwords, access tokens, or other secrets.
- Treat `.env.builder.example` as a template/reference. Treat `.env` as local runtime configuration when the example uses that convention, and inspect every value before sharing it. A generated `.env` must not contain real credentials or sensitive customer data when committed.
- Use the generated source code in accordance with the applicable INNORIX Platform service terms and agreements.
